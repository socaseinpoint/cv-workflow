§ 01

What it is, in one breath.

Ingredients × recipe → the dish. Core is truth, spec is the market, render is disposable.

cv-workflow is a system, not a one-shot prompt. CORE holds general, stable truth about you — no numbers, append-only, so specifics never become fabrication hooks. SPEC describes what a résumé should be right now — derived from verified research, hybrid prose + machine-checkable rules, parameterized by target (@master → @title → @company). The generator intersects them into the engine's cv.json; check.py enforces the spec's gates; rendering to PDF is a separate, dependency-free engine. The render is a throwaway artifact — re-generated, never hand-edited.

§ 02

Three layers, kept apart.

Mixing them is how résumés drown in overclaim.
core

Truth about you

General anchors, markdown, append-only, no numbers. Stable — it doesn't know about the market. Specifics become invention hooks, so they stay out.

spec

What the market wants

What a résumé should be now — from verified research. Prose + rules.yaml gates. Moves with the market, not with you.

evidence bank

Backed specifics

Confirmed numbers/details with provenance. Grows per application, reused — so a metric is asked once and never invented.

gap = spec − core

A roadmap, free

What the spec wants that your core lacks. Read two ways: what to surface in the CV, and what to learn or build next.

§ 03

Why it matters.

Three payoffs — one line each.
// nothing is fabricated

No fact in the CV that isn't in your core; every number rests on the evidence bank with provenance. You can defend every line in the room — because you lived it.

// the spec is researched, not guessed

What "good" means comes from adversarially-verified market research (ATS parsing, recruiter scan, the 2026 stack) — folklore and vendor-funded numbers filtered out, not copied in.

// gates run before a PDF exists

check.py hard-blocks ATS traps (multi-column, header contacts, filler phrases) and scores a 0-100 rubric (metrics, XYZ, seniority signals). Render only if it passes.

§ 04

Generate → check → render → loop.

A pipeline you re-run per role — each step is inspectable, the answer is yours.

The CV is the intersection of your facts and a researched spec — checked before it renders. Tailoring to a title or a specific JD is a light pass over the same cv.json. Re-render any time; never hand-edit the PDF. 

# the system (workflow) + the render engine (separate, stdlib-only)
git clone https://github.com/socaseinpoint/cv-workflow
git clone https://github.com/socaseinpoint/ats-cv-generator
# your facts live in data/ — never committed
python3 check.py data/master.cv.json data/spec/fullstack-ts.rules.yaml
python3 ../ats-cv-generator/render.py data/master.cv.json -o data/out/cv.pdf

Built on the arcs method and driven inside Claude Code. Your personal data stays in data/, out of git — the system is public, your facts are not.

§ 05

It separates the parts on purpose.

Truth, market, and rendering are different jobs — so each stays honest.

Plenty of tools will write you a résumé in one shot. cv-workflow doesn't. It keeps your truth (core) away from the market (spec) away from the pixels (render), so no layer can quietly corrupt another:

core stays general so numbers can't become invention hooks · spec is verified research with machine-checkable gates, not opinion · render is a separate stdlib engine (ats-cv-generator) — a disposable PDF, never the source of truth. Needs Claude Code + the arcs method. See the docs.

Core × spec → check → a CV you can defend.

Open source. Your facts stay yours; the render is disposable; nothing is invented.
